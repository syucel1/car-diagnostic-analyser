1Goals and scope

Plug a USB OBD-II adapter into the car and a laptop, open the app in Chrome, press Run scan, and watch a top-down car diagram light up system by system while a counter shows exactly how many checks have run and what each one returned. Finish with a report that separates what the car told us from what needs a human to look at.

It's a personal project that starts with the generic OBD-II basics and grows one vehicle system at a time.

Goals

  • One-click full scan of everything the connected car exposes
  • Honest progress: “23 of 41 checks · ABS timed out”, never a fake health %
  • Fault codes with plain-English meaning and freeze-frame context
  • Live readings (RPM, coolant, battery voltage, fuel trims …)
  • Maintenance and inspection log for things no ECU reports (pads, oil, filters, tyre gauge readings)
  • Scan history, compare two scans, export a PDF report
  • A demo car so anyone can try it without hardware

Non-goals (for now)

  • Clearing fault codes, actuator tests, coding, adaptations, key programming
  • Mobile browsers and Bluetooth adapters (Web Serial is desktop Chrome/Edge)
  • Coverage of every make — profiles are added one car at a time
  • Cloud accounts or sync; all data stays in the browser
  • Diagnosing why beyond well-known common causes

2How it connects

Every car sold in the EU since 2001 (petrol) / 2004 (diesel) has a standard 16-pin diagnostic socket (EOBD, the European equivalent of OBD-II), usually under the dashboard on the driver's side. A USB adapter built on an ELM327-compatible chip (genuine ELM327, or the faster STN chips in OBDLink devices) translates simple text commands into the car's bus protocol and shows up on the laptop as a virtual COM port. The browser talks to that port through the Web Serial API.

LayerChoice for v1Why
AdapterOBDLink EX (USB, STN chip, FTDI serial) — any ELM327-compatible USB adapter should workReliable, fast, well documented; cheap ELM327 clones often have buggy firmware
BrowserChrome or Edge, desktop (Windows first)Only Chromium desktop ships Web Serial; requires HTTPS or localhost
Car protocolAuto-detect (ATSP0); expect ISO 15765-4 CAN on most post-2008 carsThe adapter handles CAN, KWP2000 and ISO 9141 for us
Serial settingsTry 115200 then 38400 baud, 8N1STN adapters default high; many ELM327 clones use 38400

3What can be checked

Generic OBD-II only guarantees emissions-related data from the engine computer. Everything else (ABS, airbags, gearbox, body, tyre pressures, oil life) lives in other modules that need manufacturer-specific requests. The app treats each check's source as a first-class field so the report never implies more than it knows.

SystemChecksSourcePhase
EngineStored / pending / permanent fault codes, check-engine light, freeze frame, distance with MIL on, distance since codes clearedGeneric services 01, 02, 03, 07, 0A1–6
EmissionsReadiness monitors (catalyst, O₂ sensors, EVAP, EGR, misfire, fuel system …) — useful before an MOTGeneric 01 01, 01 415
Live engine dataRPM, speed, coolant, intake air, load, throttle, MAF/MAP, fuel trims, O₂ sensors, timing, run timeGeneric service 01 (where supported)7
Battery / chargingModule voltage (01 42) or adapter pin voltage (ATRV); cranking dip, charging voltage at idleGeneric / adapter3
OilOil temperature (01 5C, rarely supported); oil-life % and service-due countersGeneric, rare / Profile7 / 16
Vehicle identityVIN, calibration IDs, ECU nameGeneric service 093
ABS / brakesABS module fault codes, wheel-speed sensors, pad-wear warning (if the car has wear sensors)Profile UDS 19 / 2214
TyresPer-wheel pressure & temperature on cars with direct TPMS; warning-only on indirect TPMS (uses ABS wheel speeds, no pressures exist)Profile15
Gearbox, airbags, bodyModule fault codes, gearbox fluid temperatureProfilelater
Things no ECU knowsBrake pad / disc thickness, brake fluid age, oil level & condition, air / cabin / fuel filters, tyre tread depth, wipers, lightsManual inspection log + service intervals12

4Safety: read-only by construction

A diagnostic adapter can send commands that clear codes, run actuator tests, reset modules or rewrite settings. This app is a reader, and that is enforced in code, not by convention.

Rule: every byte sequence sent to the car passes through a single ReadOnlyGuard.check(request). Anything not on the allowlist throws ForbiddenRequestError before it reaches the serial port. There is no “advanced mode” switch.
AllowedBlocked (always)
OBD-II 01 current data · 02 freeze frame · 03 stored codes · 06 test results · 07 pending codes · 09 vehicle info · 0A permanent codes
UDS 19 read DTC info · 22 read data by ID · 3E tester present · 10 01 default session only
Adapter config: ATZ ATE0 ATL0 ATS0 ATH1 ATSP0 ATDPN ATRV ATI ATSH ATCRA ATST ATAT 		OBD-II 04 clear codes · 08 on-board control
UDS 11 ECU reset · 14 clear DTCs · 27 security access · 28 comms control · 2E write data · 2F I/O control · 31 routines · 34–37 up/download · 3D write memory · 85 DTC setting · 10 02/03 non-default sessions
Any unknown AT/ST command, raw ATMA bus monitor

Operational rules shown on the connect screen: car parked, handbrake on, ignition on; never scan while driving; unplug the adapter afterwards (some drain the battery). If the battery is below 11.8 V the app warns before starting. Full list in design/safety-allowlist.md.

5Architecture

Transport

  • One interface: open(), send(cmd, timeoutMs) → string[], close()
  • ElmSerialTransport: Web Serial, line framing on the > prompt, one command in flight at a time
  • SimulatorTransport: answers like an ELM327 from a scenario file, with configurable latency and failures

Protocol

  • Builds requests (0105, 1902FF) and parses replies, including multi-frame ISO-TP responses and multiple ECUs answering
  • Maps adapter errors (NO DATA, UNABLE TO CONNECT, CAN ERROR, ?) to typed results
  • Decoders are pure functions from bytes to values — easy to unit test

Scan engine

  • Discovery: protocol, VIN, which PIDs the car supports (bitmaps 0100/0120/0140…), which modules answer
  • Planner: turns discovery + profiles into an ordered list of checks, so the total is known before running
  • Runner: executes sequentially, emits events, handles timeout/retry/cancel

Profiles (data, not code)

  • generic-obd2.json applies to every car
  • Per-vehicle JSON adds modules (CAN header, e.g. ABS 7B0/7B8), DIDs and decoders by name
  • Selected by VIN prefix (WMI + model year) or picked manually

6Scan engine and progress

What the progress bar counts

The total N is fixed once planning finishes, so the counter only ever goes up: “k of N checks”. A check is one question to one module (e.g. “Engine ECU · stored fault codes”). The bar is segmented by result so the colour mix itself tells the story.

Result statusMeaningShown as
RunningRequest sent, waiting for replyPulsing zone on the car diagram
Reading receivedValid answer, nothing abnormalGreen
Fault reportedCodes present, MIL on, or value outside its normal rangeAmber
UnsupportedCar says it doesn't support this (bitmap or NO DATA / negative response 0x11/0x12/0x31)Grey, excluded from “coverage”
No responseTimed out after retries, or bus error — we don't knowRed outline; never treated as “OK”
Manual inspectionCan't be read electronically; pulled from the inspection log or flagged as to-doPurple
“ABS · no response” and “ABS · checked, 0 faults” are different outcomes and are always worded differently in the UI and the report.

Events emitted to the UI

scan:planned   { total, checks: CheckPlan[] }
check:start    { checkId, system, label, request, ecu }
check:result   { checkId, status, value?, dtcs?, raw, durationMs }
live:sample    { pid, value, unit, t }
scan:done      { scanId, summary }        // also on cancel → partial: true
scan:error     { stage, message, recoverable }

Timing

Requests are sequential (the adapter handles one at a time). Default timeout 1 s for engine requests, 2 s for other modules, one retry, adaptive timing (ATAT1). A generic scan of ~40 checks should finish in under a minute on CAN; older K-line cars are slower and the ETA adapts from measured durations.

8Data model and storage

All data is stored locally in IndexedDB. Each scan stores the raw request/response log alongside decoded results, so decoders can be improved and old scans re-decoded later.

Vehicle      { id, vin?, nickname, make?, model?, year?, profileId, tyreSpec?, odometerKm? }
Scan         { id, vehicleId, startedAt, finishedAt, adapter, protocol, partial, summary }
CheckResult  { scanId, checkId, system, label, source, status, value?, unit?, dtcs?, raw[], durationMs }
Dtc          { code: "P0171", kind: stored|pending|permanent, ecu, description, freezeFrame? }
LiveSession  { id, vehicleId, pids[], samples: [t, pid, value][] }
ServiceItem  { id, vehicleId, kind, intervalKm?, intervalMonths?, lastDoneAt?, lastDoneKm? }
Inspection   { id, vehicleId, at, kind, wheel?, valueMm?|valueBar?, note? }

Full field definitions and IndexedDB stores: design/data-model.md.

10Testing and the demo car

  • Decoders: table-driven unit tests from published PID formulas and real captured replies.
  • Guard: every blocked service has a test proving it never reaches the transport.
  • Simulator scenarios: JSON that maps requests to replies with latency and failure injection. The same files drive tests and the demo car. Scenarios: healthy car, lean engine + low tyre + brake check due, ABS offline, old K-line car, flaky adapter (random NO DATA, mid-scan disconnect).
  • Replay: every real scan's raw log can be turned into a scenario, so bugs found in the car become regression tests.
  • On the car: first real test only after the simulator suite passes; parked, ignition on, engine off, then at idle.

12Risks and open questions

RiskMitigation
Clone ELM327 adapters with buggy firmware or wrong baudRecommend an STN-based adapter; baud auto-probe; tolerant parser; “flaky adapter” scenario in tests
Manufacturer data (ABS, TPMS, oil life) is undocumentedProfiles are data files; start with one car you own; label everything by source
Newer cars block diagnostics behind a security gatewayGeneric OBD-II reads usually still work; show “module not reachable” honestly
Users read the report as a safety certificateWording and manual-inspection items make clear what was not checked
Web Serial is Chromium-desktop onlyDetect and explain on unsupported browsers; demo car still works everywhere
Adapter left plugged in drains the batteryReminder on scan finish

Open questions

  • Which car is the first target for an enhanced profile (make, model, year, TPMS type)?
  • Which adapter to buy first — OBDLink EX, or reuse an existing ELM327?
  • DTC description source: a bundled generic P0xxx list is easy; manufacturer-specific codes need per-profile tables.
  • Units: metric by default (°C, bar, km) with a setting for psi / miles?
